# 知识摄入 Source 持久同步 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 Source 管理基础上交付持久排队、并发安全的同步与可查的运行历史，支持按来源身份更新文档和仅完整成功时的缺失对账。

**Architecture:** Source job 与运行历史分表；worker 使用原子认领和 per-source 排他约束。Adapter 只发现规范化条目，协调器负责下载后 SHA 校验、Source/external key upsert、原始文件版本、Blob、解析任务及完成时缺失对账。所有条目独立提交；部分失败的 run 失败但已提交的成功条目不回滚。

**Tech Stack:** .NET 10、EF Core/Npgsql、PostgreSQL 16、Testcontainers、Cronos（标准五段 cron，UTC）。

## Global Constraints

- 先执行[基础阶段](2026-09-29-knowledge-sources-foundation.md)和[管理阶段](2026-09-29-knowledge-sources-management.md)，并核对[设计稿](../specs/2026-09-29-knowledge-ingestion-sources-design.md)。
- Source 状态仅 `never/queued/running/ok/failed`；运行记录仅 `running/ok/failed`，每 Source 最多最近 50 条。
- 保留 `(KnowledgeSystemId, Sha256)` 唯一约束和 Document 主归属 `(SourceId, ExternalKey)` 部分唯一索引；本阶段新增唯一 `(SourceId, ExternalKey)` 的绑定表作为同步身份。同一 SHA 跨 Source 不创建新行，也不覆盖原归属，但须记录每个来源的绑定。
- 完整成功枚举、所有条目提交成功且未取消，才可为本 Source 未出现的绑定设 `MissingSince`；只有至少一条绑定、全部绑定缺失且 `IsManualUpload == false` 的文档才设文档级 `MissingSince`。失败、部分扫描或取消绝不可将未出现的绑定标缺失；已经成功提交的重现条目必须立即清除其绑定及关联文档的缺失状态。
- `folder` 被动存储，不排自动扫描；`api` push 不定时拉取；仅有 adapter 的主动 kind 才可手动/定时入队。

- [ ] **Step 1: 写失败的 fake adapter 集成测试。** 预置来源 key `a` 的 doc，第一次 feed `a` 同 SHA 应 0 更新、0 文件版本；第二次相同 key 变更字节应原地更新并新增递增文件版本和解析 job；A→B→A 得到三个版本。不同 Source/key 命中同一 KS SHA 时复用原文档且不重指向其 Source、不创建第二行/版本，但写入第二条绑定；该 key 后续同 SHA 重试幂等，变更字节时改绑到新建文档，原 Source 的文档不变；同 Source 不同 key 共享时也须分叉；改为另一已占用 SHA 时改绑到已有文档而非报错。完整成功扫描 `{a,b}` 后下一次 `{b}` 仅标 `a` 绑定缺失；共享文档仍有活跃绑定时不标文档缺失，所有绑定缺失才标记；手工上传文档被同步复用后仍不可标文档缺失；失败/取消/分页未完成时不得给未出现的 key 新增缺失标记。另先用完整扫描标记 `a` 和其文档缺失，再让下一轮先成功提交同 SHA 的 `a`、随后分页失败；断言 `a` 绑定及文档的 `MissingSince` 均清空，未出现的其他绑定保持原样。用两个不同 Source 绑定同一文档，在两个独立 PostgreSQL 事务中并发完成各自的缺失扫描，断言两者提交后该文档被标记缺失；并发一方标记缺失、另一方重现时，最终文档不缺失。模拟旧 run 租约过期后新 run 已认领：旧 run 的单条 upsert 和完整扫描对账均不得提交，新 run 正常摄入/对账；并发同 key upsert 不得出现双绑定或双文档；两次同 SHA 摄入中一次事务失败、另一次尚未提交时，失败回收和文档删除都不得移除成功事务需要的 Blob。另用两个独立 PostgreSQL 事务卡在绑定插入与文档删除之间，验证无论谁先取得文档行锁，删除和 upsert 最终均有明确结果、不会留下孤立绑定或不可删文档；实际调用手工上传、同步改写与删除交错，验证不会因相反锁顺序死锁。另用真实 `SourceService.DeleteAsync` 与同 Source 单条 upsert 并发，覆盖删除先持 Source 锁和摄入先持 Source 锁两种交错；断言无死锁、无孤立绑定、删除后无摄入写入。运行 `dotnet test src/ISEStudio.IntegrationTests/ISEStudio.IntegrationTests.csproj --filter FullyQualifiedName~SourceSyncTests`，预期红灯。
